## 1. 背景与目标

UniLife OS 参加深圳理工大学 AI Agent 创新大赛，当前适配赛道四「生活帮手 Agent」。赛事延期到 2026-05-15 初赛提交、2026-05-24 线下决赛，意味着项目需要从“能演示的比赛原型”升级为“可解释、可扩展、可稳定演示的 Agent 产品原型”。

本次重构不追求推倒重写，也不追求做成完整 SaaS。核心目标是围绕赛事评分标准，将 UniLife OS 打造成一个讲得清、跑得稳、演得顺的垂直校园生活 Agent。

## 2. 参赛叙事定位

项目不应被描述为“大学生助手 App”或“ChatGPT + 记账/Todo”。更强的叙事是：

> UniLife OS 是面向大学生日常生活的个人 Agent 操作系统。它持续理解学生状态，主动发现风险，并能调用工具完成真实操作。

核心闭环：

1. 状态感知：统一读取课程、财务、健康、待办、旅行等生活状态。
2. 工具行动：通过结构化工具真实查询、记录、修改用户数据。
3. 主动关怀：根据状态变化生成预算、考试、健康、待办、旅行提醒。
4. 可视反馈：对话回复、侧边栏、数据看板同步反映状态变化。

## 3. 现状判断

当前项目已有明确优势：

- Streamlit UI 已完成基本交互闭环。
- DeepSeek function calling Agent 循环已落地。
- 24 个工具覆盖五大生活模块。
- JSON 原子写入和增量覆盖机制已有基础鲁棒性。
- 技术方案文档已经基本贴合赛道四。

当前主要问题：

- `mock_data.py` 仍承担事实数据源职责，部分日期数据已过期，影响演示可信度。
- `tools.py` 与 `app.py` 文件过大，工具 schema、执行逻辑、格式化和 UI 编排耦合较重。
- 主动提醒当前是函数式规则聚合，还未形成独立“主动关怀引擎”。
- 缺少自动化测试，难以证明鲁棒性。
- 缺少稳定 demo seed、演示脚本和评审话术映射。

当前关键文件：

- `app.py`：Streamlit 主入口，包含侧边栏、聊天、看板渲染，后续应拆到 `ui/`。
- `modules/chat_engine.py`：DeepSeek function calling Agent 循环，后续可迁移到 `agent/chat_engine.py`。
- `modules/tools.py`：24 个工具 schema 和执行路由，后续应拆成 `agent/schemas.py`、`agent/executor.py` 和分域工具模块。
- `modules/mock_data.py`：当前事实数据拼装中心，后续应拆成 seed、domain service、context summary、proactive rules。
- `modules/persistence.py`：当前 JSON 增量持久化层，后续应演进为 SQLite/repository 层。
- `prompts/system_prompt.py`：动态 system prompt 构建，后续应读取新的上下文摘要和主动提醒事件。
- `docs/技术方案文档.md`：初赛技术方案草稿，R6 阶段需要按新架构更新。
- `CLAUDE.md`：旧开发上下文和历史 Phase 记录，已增加当前重构入口。

## 4. 重构原则

1. 保留产品方向，不换技术栈。
   Streamlit 对比赛演示足够，当前阶段不重写 React/Next。

2. mock 降级为 seed。
   mock 不再扮演数据库，只作为 demo 用户初始化数据来源。真实状态统一从持久化层读取。

3. 先稳核心链路，再加功能。
   优先保证“状态读写、Agent 工具、主动提醒、看板同步、演示流程”稳定。

4. 技术亮点必须能被评委理解。
   每个重构项都要能映射到评分标准：创新性、效率、鲁棒性、实用价值、人机交互、展示效果。

5. 控制重构边界。
   当前阶段暂缓复杂多用户、权限系统、真实通知推送、大型后端服务化。

架构说明：

- `agent` 负责工具 schema、工具执行、上下文摘要和 LLM 调度。
- `proactive` 负责主动关怀事件生成、去重、节流和快报生成。
- `ui` 只负责展示和用户交互。

### Phase R1：真实持久化数据层

目标：把 mock 从事实数据源移出，建立可持久化的真实数据层。

建议实现：

- 优先使用 SQLite，避免过早引入云服务复杂度。
- 建立 demo 用户和 seed 初始化机制。
- 建立课程、财务、健康、待办、旅行五类表或实体。
- 提供一键重置 demo 数据能力。
- 所有日期改为动态生成或用户自定义，不再写死过期日期。

推荐最小数据模型：

- `profiles`：demo 用户基础信息、预算、运动目标等轻量设置。
- `courses`：课程名称、星期、时间、地点、教师、类型、是否删除。
- `transactions`：日期、项目、金额、分类、图标。
- `health_logs`：日期、步数、睡眠、饮水、运动、心情。
- `todos`：任务、截止日期、优先级、分类、完成状态。
- `travel_plans`：旅行名称、日期、预算、状态、同行人。
- `travel_itinerary`：旅行 ID、时间、活动、地点、费用、图标、排序。
- `packing_items`：旅行 ID、物品名、是否勾选。
- `proactive_events`：事件类型、严重程度、标题、原因、建议动作、是否已读、创建时间。

推荐 SQLite schema 草案：

```sql
CREATE TABLE IF NOT EXISTS profiles (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  monthly_budget REAL NOT NULL DEFAULT 2000,
  exercise_goal INTEGER NOT NULL DEFAULT 3,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS courses (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  weekday TEXT NOT NULL,
  time TEXT NOT NULL,
  course TEXT NOT NULL,
  location TEXT NOT NULL,
  teacher TEXT,
  type TEXT,
  is_deleted INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS transactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  date TEXT NOT NULL,
  item TEXT NOT NULL,
  amount REAL NOT NULL,
  category TEXT NOT NULL,
  icon TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS health_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  date TEXT NOT NULL,
  steps INTEGER NOT NULL DEFAULT 0,
  sleep_hours REAL,
  sleep_quality TEXT,
  water_cups INTEGER NOT NULL DEFAULT 0,
  exercised INTEGER NOT NULL DEFAULT 0,
  mood TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(profile_id, date)
);

CREATE TABLE IF NOT EXISTS todos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  task TEXT NOT NULL,
  deadline TEXT NOT NULL,
  priority TEXT NOT NULL,
  category TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS travel_plans (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  trip_name TEXT NOT NULL,
  date TEXT NOT NULL,
  budget REAL NOT NULL,
  status TEXT NOT NULL,
  companions TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS travel_itinerary (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_id INTEGER NOT NULL,
  sort_order INTEGER NOT NULL,
  time TEXT NOT NULL,
  activity TEXT NOT NULL,
  location TEXT,
  cost REAL NOT NULL DEFAULT 0,
  icon TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS packing_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_id INTEGER NOT NULL,
  item TEXT NOT NULL,
  checked INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS proactive_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  profile_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  severity TEXT NOT NULL,
  title TEXT NOT NULL,
  reason TEXT NOT NULL,
  suggested_action TEXT,
  dedupe_key TEXT,
  read INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
```

实现注意：

- SQLite 只用 Python 标准库 `sqlite3`，不要新增 ORM。
- 时间统一存 ISO 字符串，例如 `datetime.now().isoformat(timespec="seconds")`。
- 布尔值用 `0/1`，读取时再转换成 Python `bool`。
- `companions` 可先用 JSON 字符串保存，避免新增复杂表。
- 初期不要处理多用户，固定 demo profile id：`demo`。

推荐迁移顺序：

1. 先实现 `storage/database.py` 和 `storage/seed.py`。
2. 先迁移待办或财务一个模块，验证 UI、Agent 工具、上下文摘要是否能同时读取真实数据。
3. 再迁移课程、健康、旅行。
4. 旧 JSON 增量覆盖逻辑先保留，不要在第一步删除，等新链路稳定后再清理。

- 工具输入参数集中校验，工具输出保持结构化，再由 Agent 转自然语言。

赛事价值：

### Phase R3：主动关怀引擎

目标：把“提醒”升级为主动状态监测机制，而不是简单静态提示。

建议实现：

```text
proactive/
  rules.py       # 预算、考试、健康、待办、旅行规则
  engine.py      # 扫描状态并生成事件
  policy.py      # 去重、节流、优先级
  briefing.py    # 今日快报和 Agent 上下文摘要
```

触发时机：

- 用户打开 App 时扫描。
- 工具执行后扫描。
- 聊天前注入最新提醒。
- 后续如部署平台支持，再增加定时扫描。

关键规则：

- 预算超过 80%。
- 待办 24 小时内截止。
- 考试进入 7 天倒计时。
- 连续多天睡眠不足。
- 连续 3 天未运动。
- 旅行临近但清单未完成。

验收标准：

- 提醒事件有结构化字段：类型、严重程度、原因、建议动作、创建时间。
- 同类低优先级提醒不会频繁打扰。
- Agent 能基于提醒自然介入对话。

R3 执行约束：

- 不要先做后台线程或定时器。
- 先实现“打开 App 扫描、工具执行后扫描、聊天前扫描”三类同步触发。
- 主动提醒必须写入 `proactive_events`，不要只返回临时字符串。
- 同类提醒要有 `dedupe_key`，例如 `budget_risk:2026-04`、`todo_due:123`。

赛事价值：

- 创新性：从被动问答升级为主动关怀。
- 人机交互：提醒不过度打扰，能解释原因。
- 实用价值：覆盖学生高频风险场景。

### Phase R4：UI 拆分与演示体验打磨

验收标准：

- 5 分钟演示链路不卡顿、不迷路。

赛事价值：

### Phase R5：测试、鲁棒性与可观测性

目标：用最低成本建立可信的质量保障。

关键任务：

- 增加 `pytest`。
- 覆盖日期动态生成、预算计算、待办过滤、健康跨天/跨周、旅行清单、工具异常。
- 增加简单日志或调试面板，记录最近工具调用和主动提醒事件。
- 检查 API Key 缺失、网络异常、参数缺失、数据库读写异常的兜底体验。

验收标准：

- 核心单元测试可一键运行。
- 常见异常不会导致页面崩溃。
- 答辩中能展示“我们如何保证鲁棒性”。

赛事价值：

- 鲁棒性：直接对应 15% 评分。
- 效率：上下文裁剪、工具按需调用有证据。

### Phase R6：初赛材料与决赛演示

目标：把工程成果转化为可提交、可演讲、可演示的比赛材料。

关键任务：

- 更新 `docs/技术方案文档.md`，对齐新架构。
- 准备 5 分钟 demo 视频脚本。
- 准备答辩 PPT：问题、方案、架构、创新、演示、未来。
- 准备稳定 seed 数据和演示话术。

建议 5 分钟演示链路：

1. 打开 App，展示今日快报和主动关怀。
2. 询问“我今天怎么安排？”
3. 记录早餐和奶茶消费，预算看板实时变化。
4. 触发预算风险提醒。
5. 新增或修改待办。
6. 创建或更新周末旅行计划。
7. 用户说“我最近好累”，Agent 结合睡眠、运动、待办压力回应。

验收标准：

- 初赛文档和视频能在截止前提交。
- 决赛现场能无网络波动风险地完成核心演示。
- 项目故事能自然对应六项评分标准。

## 7. 暂缓事项

以下事项有价值，但当前不是第一优先级：

- 多用户注册登录。
- 复杂权限系统。
- 真正的 Push Notification。
- 微信、飞书、邮件等外部通知集成。
- 完整云端 SaaS 化。
- 大规模 RAG 知识库。
- 多 Agent 协作框架。

除非核心链路已稳定，否则不建议提前投入这些方向。

## 8. 近期执行建议

最近一轮应按以下顺序推进：

1. 完成 R0 文档和任务记录机制。
2. 设计 R1 数据模型，决定 SQLite schema。
3. 实现 seed 初始化和动态日期。
4. 迁移一个最小模块，例如待办或财务，验证新数据层。
5. 再逐步迁移课程、健康、旅行。

判断标准：每一步都必须能让比赛演示更稳、答辩更好讲。

## 10. 禁止事项清单

后续模型除非用户明确要求，否则不要做以下操作：

- 不要删除 `modules/mock_data.py`、`modules/persistence.py` 或旧 JSON 数据文件。
- 不要把项目从 Streamlit 改成 React、Next、FastAPI 全栈或其他新架构。
- 不要引入重量级 ORM、复杂依赖或云服务 SDK。
- 不要一次性迁移所有模块。
- 不要修改 `docs/技术方案文档.md` 来描述尚未完成的架构。
- 不要把 API Key、数据库文件、`.env` 提交进版本控制。
- 不要使用破坏性 git 命令。
