## 导读：一页看懂 UniLife OS

**一句话定位**：UniLife OS 是为大学生打造的个人 AI 生活操作系统。它把原本分散在课表、记账、待办、健康、旅行 5 类工具里的状态，统一到一个**能执行真实操作、能主动发现风险、能识别图片**的 Agent 闭环中。

**三个核心创新**：

1. **行动型 Agent + 多模态识别，而非聊天机器人**——模型不只是生成文字，而是通过 28 个结构化工具（24 文本 + 4 多模态视觉）真实读写用户生活数据。一句"中午和室友吃麻辣烫，花了 28"或一张小票照片，都能完成识别、归类、入账、预算更新、风险提示的完整链路，全程无需用户切换界面。
2. **主动关怀引擎，而非被动问答**——6 条结构化规则持续扫描用户状态（预算 / 待办 / 考试 / 睡眠 / 运动 / 旅行），用 12 小时去重 + 标为已读机制控制打扰节奏；同一事件同时驱动 UI 卡片展示和 Agent 上下文注入，让 AI 在相关话题中能自然带到状态风险。
3. **状态持久 + 动态 seed + 双模型协同，而非 mock 玩具**——用户每次操作都真实写入持久化层并影响后续对话；演示场景下日期会随当前时间滚动，永远不会出现"两个月前的样例数据"露馅；DeepSeek-V4-Flash 负责决策与回复，豆包视觉模型负责 OCR 识别，单点故障互不影响。

**项目关键数据**：

| 维度 | 数据 |
|---|---|
| 生活场景模块 | **5 类**（课程 / 财务 / 健康 / 待办与考试 / 旅行） |
| Agent 结构化工具 | **28 个**（24 文本 + 4 多模态视觉），按生活域拆分到 6 个独立模块 |

| 自动化测试 | **71 项**，覆盖动态日期 / 持久化 / 工具参数 / 规则触发 / 多模态识别五大路径 |

## 一、项目概述

UniLife OS 是一个面向大学生的 **AI 校园生活操作系统**。它以 Agent 为核心，把大学生日常生活中分散的课程、消费、健康、待办、考试和出行计划统一为一个可感知、可操作、可持续更新的个人生活状态系统。

传统校园生活工具通常只解决单点问题：课表 App 只看课程，记账 App 只记消费，待办 App 只列任务，健康 App 只展示数据。UniLife OS 的目标不是再做一个功能集合，而是构建一个能理解学生当前状态、主动发现风险并通过工具完成真实操作的 AI Agent。

用户只需要自然表达需求：

- “帮我记一笔奶茶 18 元。”
- “我今天有什么课？”
- “明天线代考试，我该怎么安排？”
- “周末想去广州玩，帮我做个预算和行程。”

系统会自动理解意图，选择合适工具，执行查询或写入操作，并把结果组织成自然语言回复。同时，系统还会根据用户状态主动提醒预算风险、考试临近、待办到期、连续睡眠不足、长期未运动、旅行清单未备齐等问题。

当前版本已经形成完整闭环：

```text
状态感知 -> Agent 决策 -> 工具行动 -> 数据更新 -> 主动关怀 -> 可视反馈
```

这使 UniLife OS 不是一个“仅仅会聊天的助手”，而是升级为一个“能管理生活状态的个人 Agent 操作系统”。

## 二、用户痛点与市场机会

### 2.1 校园生活管理的真实问题

大学生不是没有工具，而是工具太多、状态太散、行动太麻烦。

| 场景 | 真实痛点 | UniLife OS 的解决方式 |
|---|---|---|
| 课程与考试 | 课表、考试、作业散落在教务系统、群聊、截图中 | 统一课程视图，AI 可查询、增删改课程，并结合考试倒计时提醒 |
| 财务消费 | 记账链路长，预算超支后才发现 | 一句话记账，自动归类，实时计算预算使用率 |
| 健康习惯 | 步数、睡眠、喝水、运动缺少统一反馈 | 健康面板 + 快捷打卡 + 运动目标 + 主动提醒 |
| 待办管理 | 作业、社团、生活任务混在一起，容易遗漏 | 优先级分级，到期提醒，完成状态同步 |
| 出行规划 | 预算、行程、同行人、清单靠聊天记录和脑子记 | AI 生成旅行计划，写入时间线和必带清单 |

### 2.2 核心用户价值

UniLife OS 解决的是“大学生日常状态管理的最后一公里”。

它不要求用户学习复杂界面，而是允许用户用自然语言完成操作；它不只回答问题，还能调用工具修改真实状态；它不只被动等待用户发问，还能主动发现风险并给出建议。

对学生而言，UniLife OS 带来的价值包括：

- **省时间**：一句话完成记账、查课、加待办、规划旅行。
- **少遗漏**：考试、待办、预算、健康风险被系统主动发现。
- **更连续**：每次操作都会更新个人状态，下一轮对话和看板都能同步反映。
- **更贴心**：AI 的回复基于当前上下文，不是泛泛建议。

## 三、产品功能设计

### 3.1 五大生活模块

UniLife OS 当前覆盖五类大学生日常高频场景：

| 模块 | 能力 |
|---|---|
| 课程管理 | 查询今日课程、本周课表，新增、删除、修改课程，查看考试倒计时 |
| 财务管理 | 查询预算、记录消费、自动分类、预算进度和建议日限 |
| 健康管理 | 查询步数、睡眠、喝水、运动、心情，支持快捷打卡和目标设置 |
| 待办追踪 | 查询待办、添加待办、完成/恢复待办、临期提醒 |
| 旅行规划 | 查询旅行计划、创建/修改计划、管理行程站点和必带清单 |

### 3.2 28 个 Agent 工具（24 文本 + 4 多模态）

系统内置 28 个结构化工具，让 AI 不只是"生成文字"，而是能够通过文本指令或上传图片执行真实操作。

```text
课程管理：query_schedule / add_course / delete_course / update_course
财务管理：query_finance / record_expense / set_budget
健康管理：query_health / record_water / record_exercise / record_mood
          record_steps / record_sleep / set_exercise_goal
待办考试：query_todos / toggle_todo / add_todo / query_exams
旅行规划：query_travel / update_travel / add_itinerary_stop
          delete_itinerary_stop / update_itinerary_stop / update_packing
多模态视觉：record_expense_from_image    （拍小票自动记账）
            import_courses_from_image     （拍课表批量导入）
            log_food_calories             （拍食物估算卡路里）
            check_packing_from_image      （拍行李对照旅行清单）
```

这些工具构成了 UniLife OS 的行动边界：用户的自然语言或图片需求会被模型转化为结构化工具调用，工具执行后写入数据层，再反映到 UI、看板和后续上下文中。多模态视觉工具是链式调用——先经豆包 vision 识别图片为结构化 JSON，再调用下游持久化工具（如 record_expense / add_course），实现"图片→数据→状态"的端到端自动化。

### 3.3 三种交互方式

UniLife OS 同时支持三类入口，覆盖不同使用习惯：

- **AI 对话**：适合复杂需求和自然语言操作，例如“帮我分析这个月花销”。
- **数据看板**：适合快速了解状态，例如预算比例、健康趋势、旅行时间线。
- **侧边栏快捷操作**：适合高频低成本动作，例如喝水、运动、记心情、勾待办。

### 3.4 主动关怀

系统内置主动关怀引擎，会持续扫描用户状态并生成结构化提醒。

| 主动事件 | 触发逻辑 | 用户价值 |
|---|---|---|
| 预算风险 | 月预算使用超过 80% | 防止月底超支 |
| 待办到期 | 待办今天或明天截止 | 减少作业和事务遗漏 |
| 考试临近 | 考试进入 7 天倒计时 | 提前安排复习 |
| 睡眠不足 | 连续多天睡眠低于健康基线 | 提醒调整作息 |
| 运动缺失 | 连续多天未运动 | 促进健康习惯 |
| 出行清单 | 旅行临近但清单未备齐 | 降低出行遗漏 |

主动提醒不是简单弹窗，而是带有触发原因和建议动作，并支持已读和去重，避免重复打扰。

## 四、系统架构方案

### 4.1 架构总览

UniLife OS 采用轻量单体架构实现快速落地，同时在内部进行清晰分层，保证可维护和可扩展。

```text
用户层
  浏览器 / PWA 主屏幕入口

表现层
  AI 对话、数据看板、侧边栏快捷操作、主动关怀卡片

Agent 层
  DeepSeek-V4-Flash function calling
  多轮工具调用决策
  28 个结构化工具（24 文本 + 4 多模态）
  豆包视觉模型链式接入

状态感知层
  实时上下文摘要
  主动关怀规则扫描
  事件去重与已读管理

数据层
  动态演示数据模板
  用户增量状态
  JSON 原子持久化

测试与观测层
  自动化测试
  工具调用记录
  主动事件记录
```

### 4.2 关键技术链路

UniLife OS 的每一次对话都跑完下面这条闭环，任何一个环节都可以被单独测试和可视化。

```text
用户自然语言输入
        │
        ▼
┌─────────────────────────────────────────────┐
│  ① 上下文构建                                  │
│     • 聚合 7 类生活状态摘要                     │
│       (课程 / 财务 / 健康 / 待办 / 考试 / 旅行)   │
│     • 拉取最近 5 条未读主动关怀事件              │
│     • 组装成 System Prompt 注入模型             │
└────────────────┬────────────────────────────┘
                 ▼
┌─────────────────────────────────────────────┐
│  ② Agent 决策 (最多 5 轮循环)                  │
│     DeepSeek-V4-Flash function calling               │
│                                                │
│     ├─ 需要调用工具 → 进入 ③                   │
│     └─ 无需工具     → 生成最终自然语言回复      │
└────────────────┬────────────────────────────┘
                 ▼
┌─────────────────────────────────────────────┐
│  ③ 工具执行与状态更新                          │
│     • 参数类型 / 边界校验                       │
│     • 异常兜底 (未知工具 / JSON 解析 / 运行时)    │
│     • 读 mock_data / 写 persistence             │
│     • 收尾钩子:主动关怀规则扫描 (6 条)            │
└────────────────┬────────────────────────────┘
                 │
                 │  工具结果回传模型
                 └───────→ 回到 ②
                            ⋮
                            ▼
                 最终回复 + UI 卡片同步 + 看板同步 + 主动提醒更新
```

这条链路的关键设计在于：**工具结果会以 `role=tool` 的消息形式回传给模型**，让下一轮的决策建立在真实执行结果之上而不是模型的推测；同时**每次工具执行后触发的主动关怀扫描**让 Agent 的行动和用户状态变化之间形成了正向反馈——记完一笔消费如果预算超过 80%，下一轮对话里模型就能自然引用这条新触发的事件。

### 4.3 架构设计优势

本项目的架构重点不是追求复杂技术堆叠，而是在比赛场景下实现“可演示、可解释、可扩展、可验证”的平衡。

- **可演示**：动态 seed 数据随日期滚动，演示时就如同日常使用一般可实时交互。
- **可解释**：Agent 工具、主动事件、数据变化都有清晰链路，评审可以看到 AI 如何行动。
- **可扩展**：28 个工具按生活领域模块化组织（24 文本 + 4 多模态），未来可以继续扩展图书馆、食堂、宿舍、社团等工具。
- **可迁移**：当前 JSON 持久化适合 MVP，数据结构可平滑迁移到 PostgreSQL 和多用户体系。
- **可验证**：核心逻辑已有自动化测试覆盖，降低现场演示翻车风险。

### 4.4 工程目录结构

UniLife OS 的代码按职责清晰分层。表现层不直接访问持久化，Agent 工具不耦合 UI，主动关怀引擎独立成包。这种边界让团队协作、单元测试和后续扩展都更可控。

```text
┌──────────────────────────────────────────────────────────────┐
│  ① 表现层  ui/                                                │
│     sidebar · chat · dashboard · components · styles           │
│     负责页面布局、交互控件、可观测性展示                          │
├──────────────────────────────────────────────────────────────┤
│  ② Agent 层  agent/                                           │
│     schemas (工具注册表) + executor (执行入口,含观测 + 兜底)      │
│     tools/ course · finance · health · todo · travel (共 24 工具) │

│  ③ 主动关怀引擎  proactive/                                   │
│     events (事件结构 + 持久化封装)                              │
│     rules  (6 条规则)                                          │
│     engine (扫描 + 12h 去重 + 未读列表)                          │
├──────────────────────────────────────────────────────────────┤
│  ④ 数据与上下文层  modules/                                   │
│     seed_data       动态日期 seed 模板                          │
│     context_builder LLM 上下文摘要                              │
│     mock_data       聚合层 (seed + 用户增量)                     │

│     chat_engine     DeepSeek Agent 循环                         │

调用规则：
```

### 4.5 工程化收益

为支撑赛事评审与后续多人协作，项目在工程组织上进行了系统化重构：

| 项 | 重构前 | 重构后 |
|---|---|---|
| 主入口 `app.py` | 735 行(UI + 业务 + CSS 全混合) | 49 行(仅页面配置 + 路由) |
| 工具体系 `modules/tools.py` | 1261 行(24 工具 + schema + 路由全单文件) | 16 行 facade + 5 个生活域模块 |
| 视图层 | 与主入口耦合 | 独立 `ui/` 包,5 个视图模块 |
| 主动关怀 | 函数式硬编码规则,无去重 | 独立 `proactive/` 引擎,事件结构 + 12h 去重 |
| 数据演示 | mock 日期硬编码,易过期露馅 | 动态 seed + 演示重置脚本 |
| 自动化测试 | 无 | 71 项 pytest 用例 |

工程结构的清晰分层带来三点直接收益:

- **演示稳定**:动态 seed + 演示重置脚本让现场 demo 可重复,不会因为日期过期或上一次试跑残留而露馅。
- **可扩展性**:新增工具只需在 `agent/tools/` 加一个域文件并实现 `register()`,不必动主入口或路由代码。
- **可移交性**:每个模块都有清晰的输入/输出边界,团队成员能快速接手而不需要通读全部代码。

## 五、核心技术亮点

### 5.1 从聊天机器人到行动型 Agent

UniLife OS 的核心是 function calling 驱动的行动闭环。模型不仅生成回复，还会根据用户意图选择工具并执行真实操作。

示例：

```text
用户：“帮我记一笔奶茶 18 元，顺便看看这个月花了多少。”

Agent 行动：
1. 调用 record_expense，写入一条消费记录。
2. 调用 query_finance，读取最新预算状态。
3. 生成回复，说明已记账、本月已花、剩余预算和建议日限。
```

技术控制：

- 最多 5 轮连续工具调用，防止无限循环。
- 工具结果回传给模型，使最终回复基于真实执行结果。
- 工具调用过程可在界面中展开查看，便于展示 Agent 决策链路。

### 5.2 动态上下文注入

每次对话前，系统都会把用户最新状态整理为结构化上下文，包括：

- 今日课程和近期考试。
- 本月预算、已花、剩余、建议日限。
- 步数、睡眠、喝水、运动目标、心情。
- 未完成待办和紧急事项。
- 当前旅行计划和预算。
- 未读主动关怀事件。

这使模型能够基于当前生活状态回答，而不是给出泛泛建议。

例如用户说“我今天好累”，系统可以结合“睡眠不足、近期考试、待办到期、连续未运动”等状态，给出更贴近用户处境的建议。

### 5.3 动态 seed + 增量持久化

比赛 Demo 最大的风险之一是数据“看起来是假的”：日期过期、状态不变、试跑污染。UniLife OS 采用动态 seed + 增量持久化解决这个问题。

```text
动态 seed
  提供课程、消费、健康、待办、考试、旅行等基础演示数据
  日期会根据当前时间自动滚动

用户增量
  只保存用户新增、修改、删除、打卡、记账等变化

聚合视图
  每次读取时将 seed 与用户增量合并
  形成当前真实状态快照
```

该设计兼顾了演示稳定性和真实交互感：演示前可以恢复干净状态，演示中用户操作又会真实影响系统状态。

### 5.4 主动关怀事件引擎

UniLife OS 的重要创新点是把"提醒"从 UI 逻辑升级为结构化事件系统。

每条主动关怀事件包含：

- 事件类型。
- 严重程度。
- 标题。
- 触发原因。
- 建议动作。
- 去重标识。
- 创建时间。

整个事件生命周期如下：

```text
  [规则扫描]  6 条 check_* 规则并行评估当前状态
  check_budget_risk / check_todo_due / check_exam_near
  check_sleep_short / check_exercise_missing / check_travel_packing
                    │
                    ▼
  [去重判定]  同 dedupe_key 是否在 12 小时内已触发?
                    │
          ┌─────┴─────┐
         是              否
          │               │
     跳过不写       upsert 到 persistence
                         │
                         ▼
  [双出口分发]  同一事件同时服务于两个消费方
                    │
          ┌─────┴─────────┐
          ▼                ▼
   ┌───────────┐    ┌─────────────┐
   │   UI 侧          │    │  Agent 侧           │
   │  顶部卡片        │    │  进入 System Prompt │
   │  前 3 条展示    │    │  前 5 条注入上下文 │
   │  带建议动作     │    │  让模型在相关话题   │
   │  "标为已读" 按钮│    │  自然带到风险       │
   └─────┬────┘    └─────────────┘
            │
            │  用户点击 "标为已读"
            ▼
   events.mark_read(dedupe_key)
            │
            ▼
   加入 proactive_read_keys
            │
            ▼
   list_unread() 不再返回该事件,  UI 和 LLM 上下文都同步消失
```

系统会对同类事件进行 12 小时去重，避免重复打扰。用户也可以将事件标为已读。主动事件同时服务于两个入口：一方面显示在页面顶部卡片中，另一方面进入 AI 上下文，使模型能在相关话题里自然提及。

### 5.5 工程化工具体系

28 个 Agent 工具不是写在一个大函数里，而是按生活领域拆分和注册：

- 课程工具（4 个）。
- 财务工具（3 个）。
- 健康工具（7 个）。
- 待办与考试工具（4 个）。
- 旅行工具（6 个）。
- **多模态视觉工具（4 个）**：链式调用豆包视觉 → 持久化层。

统一执行入口负责参数检查、异常兜底、调用记录和主动扫描触发。这让系统具备更强的工程可维护性，也方便未来新增工具和接入真实校园服务。

### 5.6 PWA 移动端入口

UniLife OS 提供 Web App Manifest 和 Service Worker（位于 `.streamlit/static/` 目录下的 `manifest.json` 与 `sw.js`），支持添加到手机主屏幕，以独立窗口方式打开。

在当前 MVP 中，PWA 主要用于增强移动端演示体验和日常入口；完整离线缓存、系统级推送和多端同步将在产品化阶段通过前后端分离架构进一步完善。

### 5.7 多模态接入与双模型协同

UniLife OS 在文本 Agent 之外新增了一条**多模态识别链路**，让用户可以直接拍照完成原本需要手动录入的高频任务——拍小票自动记账、拍课表批量导课、拍食物估算热量、拍行李对照旅行清单。

**双模型分工**：

| 模型 | 角色 | 调用接口 | 能力 |
|---|---|---|---|
| **DeepSeek-V4-Flash** | 决策 + 自然语言回复 | OpenAI SDK + DeepSeek 官方 base_url | function calling、上下文推理、回复生成 |
| **豆包视觉模型** | 多模态识别 + 结构化抽取 | OpenAI SDK + 火山方舟 Volces Ark base_url | 图片 OCR、图文理解、JSON 输出 |

两者都通过 OpenAI 兼容 SDK 调用，差异只在 base_url 和 model 字段，实现成本极低。

**调用链路**：

```text
用户输入：文本 / 文本 + 图片
        │
        ▼
┌──────────────────────────────────────────────────┐
│  ① UI 层 ui/chat.py                                │
│     • 文本走原 chat_input                           │
│     • 图片走 file_uploader（jpg/jpeg/png）          │
│     • Pillow 自动压缩到 ≤ 1024px / JPEG q=80        │
│     • base64 编码后存 session_state.pending_image_b64│
└─────────────────┬────────────────────────────────┘
                  ▼
┌──────────────────────────────────────────────────┐
│  ② DeepSeek V4-Flash 决策层                         │
│     • 用户消息含 [系统消息：用户已上传图片...] 标记  │
│     • 模型选择 4 个 vision 工具之一                  │
│     • image_b64 参数留空，由 UI 包装层注入          │
└─────────────────┬────────────────────────────────┘
                  ▼
┌──────────────────────────────────────────────────┐
│  ③ 链式工具层 agent/tools/vision.py                 │
│     ① base64 解码 → bytes                          │
│     ② modules/vision.py 调豆包 chat.completions     │
│        + image_url content block + 文字 prompt     │
│     ③ 豆包返回 JSON 字符串（剥 markdown 包装）       │
│     ④ json.loads → 字段校验 + 置信度门槛            │
│     ⑤ 链式调用持久化工具（add_expense / add_course / │
│        ...）                                        │
│     ⑥ 返回友好的自然语言摘要                         │
└─────────────────┬────────────────────────────────┘
                  ▼
        状态更新 → 主动关怀扫描 → UI/看板同步
```

**4 个多模态工具**：

| 工具 | 触发场景 | 链式动作 | 置信度门槛 |
|---|---|---|---|
| `record_expense_from_image` | 拍小票/账单 | 识别 amount/item/category → `add_expense` | ≥ 0.5 |
| `import_courses_from_image` | 拍课表截图 | 识别 courses → 多次 `add_course`（自动去重） | — |
| `log_food_calories` | 拍食物 | 识别 name/calorie → 仅返回文本（不入库） | ≥ 0.4 |
| `check_packing_from_image` | 拍行李 | 对照当前旅行 packing_list → 返回 found/missing/extra | — |

**鲁棒性保障**：

- **三类错误兜底**：未配 KEY / 网络异常 / JSON 解析失败 全部返回 dict 含 `error` 字段，绝不抛 traceback。豆包偶尔返回 markdown 代码块包装的 JSON，`_strip_markdown_codeblock` 会剥掉。
- **置信度门槛拒识**：模型识别置信度过低时不写库，给出友好提示让用户重拍或改用文字。
- **图片压缩**：客户端压到 ≤ 1024px JPEG q=80，平均 50-150KB base64，控制 token 消耗与传输延迟。
- **session 隔离**：image_b64 不进 DeepSeek context（避免 50K+ token 浪费），通过 ui/chat.py 的 `_exec_with_image` 包装层在工具执行的最后一公里注入。

**测试覆盖**：

`tests/test_vision.py` 16 条用例（占总用例 24%）覆盖：模型 mock 正常路径 / JSON 解析失败 / 网络异常 / KEY 缺失 / 非法分类回退 / markdown 剥离 / 多课程 / packing 三段分类 / 链式 record_expense 写库 / 低置信度拒识 / 链式 import_courses 写 extra_courses / 非法 base64 / 空 image_b64。所有用例都用 `unittest.mock.patch` 替换豆包 client，0.32 秒内全过，不依赖网络。

## 六、鲁棒性与可信度

### 6.1 安全与容错

| 风险 | 处理方式 |
|---|---|
| JSON 写入中断 | 采用临时文件 + 原子替换，避免数据写坏 |
| 磁盘或权限异常 | 写入失败时降级处理，不直接中断应用 |
| API Key 缺失 | 给出清晰提示，不抛出长错误栈 |
| 网络或模型异常 | 返回友好错误，保留已执行工具记录 |
| LLM 参数异常 | 工具层做类型和边界校验 |
| 重复提醒 | 主动事件 12 小时去重，可标记已读 |
| 对话过长 | 裁剪历史上下文，控制 token 和延迟 |

### 6.2 参数边界控制

系统对关键输入做边界保护：

- 金额必须大于 0 且不超过合理上限。
- 步数、睡眠时长、运动目标有明确范围。
- 课程和行程删除前先确认目标存在。
- 多个模糊匹配结果会返回提示，而不是随机修改。
- 工具异常不会让对话崩溃，而是包装成可理解的错误。

### 6.3 自动化测试

UniLife OS 不依赖人工冒烟保障质量，而是把核心业务逻辑写入了 71 项自动化回归测试，分布在五个测试模块中：

| 测试模块 | 用例数 | 覆盖内容 |
|---|---|---|
| 动态日期 | 21 | mock seed 在月初、月末、月中、周一、周六五个临界日下，消费 / 待办 / 考试 / 旅行的日期都能合理滚动 |
| 持久化 | 10 | 默认结构、记账写入、待办状态覆盖、喝水跨天重置、运动跨周重置、同日防重复打卡、待办 ID 唯一性、主动事件 upsert / 已读、聊天图片 bytes 清理 |
| Agent 工具 | 16 | 28 工具数量、未知工具兜底、参数类型守卫、消费 / 步数 / 睡眠 / 运动目标边界、查询类返回非空、新增 / 删除课程、创建旅行 + 行程站点、待办 deadline 归一化 / 拒绝非法日期 |
| 主动关怀 | 8 | 6 条规则全部存在并返回事件、12 小时去重、已读隔离、13 小时后去重过期、`get_alerts` 字段兼容、5 条上限、单规则异常不影响其他 |
| 多模态视觉 | 16 | mock 豆包 client、4 个识别函数正常路径 / JSON 解析失败 / 网络异常 / KEY 缺失 / markdown 剥离 / 非法分类回退 / 链式工具写库 / 低置信度拒识 / 非法 base64 兜底 |

测试在隔离的临时数据目录中运行，不污染真实数据。整套测试 0.4 秒内全部通过（多模态测试全部用 mock，无外部网络依赖）。

这意味着 UniLife OS 不只是"能跑的 Demo"，而是具备基础工程质量保障的 MVP——任何后续修改都可以通过回归测试验证未破坏现有能力。

### 6.4 演示可观测性

为了让 Agent 的"黑盒决策"对评审和用户都可解释，系统内置一个**演示可观测性面板**。在演示模式下，侧边栏会展示两个透明化窗口：

- **「最近 5 次工具调用」**：每条记录包含工具名、参数、返回结果片段、时间戳和成功 / 失败标识。评审现场可以看到 AI 听到一句话之后，到底调用了哪些工具、传了什么参数、得到什么结果。
- **「最近 3 条主动关怀事件」**：每条记录包含严重度、标题、去重键、触发原因，让"为什么系统现在弹出这条提醒"完全可追溯。

同模式下还附带一个**一键演示重置**按钮：把用户增量数据回到干净 seed 态，让现场反复演示不会被上一次试跑污染。

可观测性 + 重置能力共同构成了"演示稳定性"的双保险，也让 Agent 的行动透明化、可信。

## 七、人机交互设计

### 7.1 设计目标

UniLife OS 的界面不是传统管理后台，而是一个面向学生的生活中控台。设计目标是：

- 状态一眼可见。
- 操作一步完成。
- AI 行动过程可理解。
- 主动提醒不过度打扰。

### 7.2 交互亮点

- **主动关怀卡片**：在页面顶部展示系统发现的重要事项，并给出建议动作。
- **动态欢迎语**：首次进入对话时，自动生成当天课程、财务、待办、健康快报。
- **工具调用可视化**：AI 执行工具时显示调用过程和结果。
- **快捷打卡**：喝水、运动、心情、待办完成等高频动作无需进入复杂表单。
- **数据看板**：用图表展示消费构成、步数趋势、睡眠变化和旅行时间线。
- **多模态识别**：聊天框上方的「📷 上传图片」入口支持拍小票自动记账、拍课表批量导入、拍食物估卡路里、拍行李对照旅行清单——一张图就能完成原本要 5 步操作的事。

### 7.3 视觉风格

R8 阶段将原有 Streamlit 模板感界面收敛为「构成主义启发的现代极简 + 克制拟态」：全局使用暖米色纸面、暖棕黑正文、Anthropic coral 品牌色；首屏采用双卡 hero，右侧 4 宫格数字面板展示今日课程、待办压力、预算使用和运动周频；主动关怀、侧边栏、数据看板 metric 都统一使用 warm surface、1px hairline、顶部 inset 内高光和低透明度软阴影。

这套视觉不是单纯装饰，而是服务交互层级：主数字使用更大的 display 字体，已花费、睡眠质量、目标步数等 delta 辅助信息降权；侧边栏保留紧凑卡片密度，数据看板保留更大的主体数字，便于评审和用户在 5 秒内扫到状态重点。

### 7.4 移动端体验

项目支持 PWA 主屏幕入口，图表禁用缩放误触，聊天区域和输入区域适配移动端展示。当前版本已经具备移动端演示可用性，后续会在产品化阶段升级为小程序或原生 App。

## 八、典型场景演示

### 场景 1：晨间快报

**传统方式**：打开课表 App 看今天的课 → 切到记账 App 看本月预算 → 切到待办 App 查紧急任务 → 切到健康 App 看睡眠数据 → 翻群聊找明天考试通知。跨 5 个 App，约 3 分钟，还经常漏看。

**UniLife OS**：

```text
用户打开 UniLife OS。

系统自动汇总：
- 今天有哪些课。
- 本月预算是否紧张。
- 哪些待办今天截止。
```

### 场景 2：一句话记账

**传统方式**：打开记账 App → 点"新增" → 选分类（餐饮）→ 输入金额（28）→ 填备注（麻辣烫）→ 保存 → 跳到预算页计算还剩多少。约 30 秒、6 步操作。

```text
用户：“中午和室友吃麻辣烫，花了 28。”

系统动作：
1. 自动识别金额、项目和分类。
2. 写入消费记录。
3. 更新预算使用率。
4. 如果预算紧张，触发主动提醒。
```

用户价值：把传统记账 App 的多步操作压缩为一句话，并且在记录的同时联动预算分析和风险提醒，整个链路 5 秒完成。

### 场景 3：考前关怀

**传统方式**：考前焦虑 → 自己列复习计划 → 自己估算能学多久 → 熬夜复习顾不上健康 → 第二天状态差。整个过程没有系统帮你做综合判断。

**UniLife OS**：

```text
用户：“明天线代考试，我现在有点慌。”

系统结合：
- 考试时间和地点。
- 今日课程。
- 睡眠状态。
- 待办压力。

输出：
- 复习重点建议。
- 时间安排建议。
- 作息提醒。
```

用户价值：AI 不只是安慰，而是基于真实状态给出可执行计划——比如知道你过去 3 天睡眠不足，会优先建议早睡而不是熬夜冲刺。

### 场景 4：周末旅行规划

**传统方式**：自己列大致想去哪 → 微信问同行人 → 大众点评查商家 → 高德地图算路线 → 备忘录记清单 → 微信反复确认。信息散在 5+ 个工具里，最后还是脑子里"大概记得"。

**UniLife OS**：

```text
用户：“周末想去广州玩，预算 500，帮我安排一下。”

系统动作：
1. 创建旅行计划。
2. 添加多个行程站点。
3. 估算预算。
4. 生成必带清单。
5. 在看板中同步展示旅行时间线。
```

用户价值：从"生成建议"走向"写入计划"，让 AI 真正成为生活管理入口。下次打开看板 Tab，行程时间线和必带清单都在那里，无需重新整理。

### 场景 5：拍照入数据（多模态）

**传统方式**：在便利店买完东西 → 撕下小票 → 打开记账 App → 输入 6 个字段 → 保存 → 关闭。等到月末才发现："我这个月怎么花了这么多？"。或者新学期拿到课表照片 → 一门门往课表 App 里手动输入 → 漏一节课就会错过。

**UniLife OS**：

```text
用户在聊天框上方点「📷 上传图片」→ 选一张刚拍的小票。
（图片本地 Pillow 自动压到 ≤ 1024px JPEG q=80）

输入 "记一下"，发送。

系统动作：
1. DeepSeek-V4-Flash 看到 [系统消息：用户已上传图片] 标记。
2. 选择 record_expense_from_image 工具。
3. UI 包装层把 base64 注入工具参数。
4. 链式调用 modules/vision.py → 豆包 vision OCR。
5. 模型返回 {amount: 28, item: "麻辣烫", category: "餐饮", confidence: 0.92}。
6. 置信度过 0.5 门槛 → 自动调 add_expense 写入持久化。
7. 触发主动关怀扫描，预算超 80% 时弹出新提醒。
8. 回复用户："已记账：麻辣烫 ¥28（餐饮），本月还剩 ¥350，注意控制～"
```

**同样的入口可以做**：

- **拍课表** → `import_courses_from_image` → 一次导入整学期课表，自动跳过已存在课程。
- **拍食物** → `log_food_calories` → 估算热量 + 给出健康建议。
- **拍行李** → `check_packing_from_image` → 对照当前旅行计划清单返回 missing/extra。

用户价值：把"识别 → 归类 → 输入 → 保存 → 联动提醒"这条平时要 30 秒 6 步操作的链路，压缩为"上传图片 + 一句话"约 5 秒——而且全程不用切应用、不用记路径、不用看预算还剩多少。这才是 AI Agent 真正"减少摩擦"的样子。

## 九、技术栈

| 类别 | 技术选型 | 作用 |
|---|---|---|
| 前端与应用 | Streamlit | 快速构建可交互 Web 应用、侧边栏、Tab 和对话界面 |
| AI 决策模型 | DeepSeek-V4-Flash | OpenAI 兼容 function calling，驱动 Agent 决策与回复 |
| AI 视觉模型 | 豆包视觉（火山方舟 Volces Ark） | OpenAI 兼容多模态 chat completions，OCR 识别小票/课表/食物/行李 |
| API 客户端 | OpenAI Python SDK | 标准化调用，便于未来切换兼容模型 |
| 数据可视化 | Plotly | 消费、步数、睡眠等图表 |
| 数据处理 | Pandas | 看板数据整理 |
| 图片处理 | Pillow | 客户端压缩到 ≤ 1024px JPEG q=80，控制 token 消耗 |
| 持久化 | JSON + 原子写入 | 单用户 MVP 的轻量可靠存储 |
| 移动入口 | PWA Manifest + Service Worker | 手机主屏幕入口和离线回退 |
| 测试 | Pytest | 核心业务逻辑回归测试，71 项覆盖文本 + 多模态全链路 |

技术栈选型的核心考量是**MVP 落地速度 × 可演示性 × 可演进性**的平衡：Streamlit 让前后端一体化开发节省了至少 60% 的 UI 工程时间；DeepSeek-V4-Flash 在 function calling 上速度比 V3 标准版快 ~2x，工具决策准确率显著提升；豆包视觉模型在中文小票 / 课表 OCR 场景下表现优于通用多模态模型，且通过 OpenAI 兼容 SDK 调用，与 DeepSeek 共享同一套客户端代码；JSON 持久化在 MVP 阶段已被证明足够稳定，并保留了向 PostgreSQL / 多用户体系迁移的路径。整个技术栈没有任何"研究型"赌注，全部是经过工业验证的成熟组合，且双模型分工清晰：DeepSeek 负责"决策"，豆包负责"看"，单点故障互不影响。

## 十、竞争优势

### 10.1 整体对比

| 能力维度 | 普通聊天助手<br/>(如 ChatGPT) | 传统校园 App<br/>(课表 / 记账类) | 简单日程<br/>记账应用 | **UniLife OS** |
|---|:---:|:---:|:---:|:---:|
| 写入用户真实数据 | ✗（只生成文字） | △（仅限自身模块） | △（仅自身模块） | **✓ 28 工具跨模块** |
| 理解当前生活状态 | ✗（无上下文） | △（只看自身数据） | ✗ | **✓ 7 类状态实时摘要** |
| 主动发现风险 | ✗ | △（如预算超额） | ✗ | **✓ 6 条规则跨模块扫描** |
| 多模块联动 | ✗ | ✗（每个 App 单点） | ✗ | **✓ 一句话跨课程/财务/健康** |
| 状态持久化 | ✗ | ✓ | ✓ | **✓ 操作即时影响后续对话** |
| 自然语言操作 | ✓ | ✗（必须填表） | ✗ | **✓ 一句话完成 N 步操作** |
| **多模态识别（拍照入数据）** | △（仅描述图片） | ✗ | ✗ | **✓ 拍小票/课表/食物/行李 → 自动入库** |
| 双模型协同 | ✗ | n/a | n/a | **✓ DeepSeek 决策 + 豆包视觉** |
| 演示稳定性 | n/a | n/a | n/a | **✓ 动态 seed + 一键重置** |
| 工程可观测性 | n/a | ✗（黑盒） | ✗ | **✓ 工具调用 + 事件可追溯** |

### 10.2 相比普通聊天助手

普通聊天助手主要依赖模型生成文字，缺少真实状态和可执行动作。UniLife OS 通过 28 个工具（含 4 个多模态视觉工具）让模型能够查询、写入、修改用户生活数据，并在 UI 中同步反馈。

### 10.3 相比传统校园工具

传统工具通常是孤立模块，用户需要自己切换 App、输入表单、判断优先级。UniLife OS 将这些模块统一到 Agent 中，让用户通过自然语言完成跨模块操作。

### 10.4 相比简单日程/记账应用

UniLife OS 不只记录数据，还能基于数据主动发现风险。例如预算紧张、考试临近、长期未运动，这些状态会被系统自动扫描并转化为可执行建议。

### 10.5 技术护城河

当前版本已经形成五层技术积累：

- **工具体系**：28 个结构化工具覆盖校园生活核心场景，含 4 个多模态视觉链式工具。
- **多模态识别体系**：DeepSeek 决策 + 豆包视觉的双模型分工，让 Agent 同时拥有"思考"和"看"的能力，并通过链式工具直接将识别结果落到持久化层。
- **上下文体系**：实时状态注入，让 AI 理解用户当前处境。
- **主动事件体系**：从被动问答升级为主动关怀。
- **状态持久体系**：用户每次操作都会影响后续对话和看板。

这五层能力共同构成 UniLife OS 的差异化护城河——单独任何一层都不难做，但把它们串成一个能演示、能扩展、有测试覆盖的闭环才是真正的工程门槛。

当前能力：

- 自动化测试和演示重置。

目标：从个人原型升级为多用户校园生活平台。

## 十二、总结

UniLife OS 的核心创新，是把大学生活中分散的数据和动作统一进一个 Agent 闭环。

它具备：

- **可行动的 Agent**：28 个工具（24 文本 + 4 多模态）让 AI 能真实查询和修改状态，支持文字与拍照双输入。
- **可理解的上下文**：每轮对话都注入实时生活数据。
- **可主动的关怀**：系统主动发现预算、考试、健康、待办、旅行风险。
- **可视化的反馈**：对话、看板、侧边栏、主动卡片同步展示状态。
- **可扩展的架构**：当前 MVP 可演进为多用户校园 SaaS 和校园 Agent OS。

UniLife OS 不只是一个校园助手 Demo，而是一个面向大学生活场景的个人 Agent 操作系统雏形。它从真实校园痛点出发，用可执行工具和主动关怀机制，让 AI 从“回答问题”走向“管理生活”。
