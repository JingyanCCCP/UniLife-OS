## 0. 给接手 AI 的交接协议

### 0.1 5 分钟开工检查

1. 读完本节 0.1 / 0.2 / 0.3 三段。
2. 跳到第 4 节「任务卡队列」，找到状态为 `激活` 的那张卡。其他卡都先不读。
3. 读 `docs/开发记录.md` 末尾最近一条记录，理解上一位接手 AI 在哪里收的笔。
4. 运行 `git status --short`，确认没有别人未提交的脏改动。
5. 读当前任务卡的「允许改动文件」「禁止改动文件」「验收命令」三个字段。**只动允许列表里的文件。**

### 0.2 推进单张任务卡的标准流程

```
读卡片 → 写代码 → 跑验收命令（4 项必须全过）→ 更新开发记录 → 把卡片状态由「激活」改为「完成」→ 把下一张「排队」改为「激活」
```

任何一步卡住超过 30 分钟，先停下来汇报，不要硬怼。

### 0.3 收尾清单（每张卡完成时）

- [ ] `git status` 已查看，未改动的禁区文件保持干净

### 0.4 兜底流程（卡片不够清楚或拿不准下一步）

1. 不要凭感觉扩展改动范围。
2. 在 `docs/开发记录.md` 末尾写一条「⚠️ 阻塞」记录，说明：当前卡 ID、阻塞点、需要的额外信息或决策。

## 3. 目标架构（R7+R8 完成后）

### 3.1 多模态调用链路

```
┌──────────────────────────────────────────────────────────┐
│  用户输入：文本 / 文本 + 图片                              │
└──────────────────────┬────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│  ① UI 层 ui/chat.py                                       │
│     • 文本走原 chat_input                                 │
│     • 图片走 file_uploader / camera_input                  │
│     • 两者合并：image_b64 + text_prompt                    │
└──────────────────────┬────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│  ② DeepSeek V4-Flash 决策层                                │
│     • 看到 image_b64 → 倾向调用 vision_* 工具              │
│     • 看到纯文本 → 走原 24 个工具的旧路径                   │
│     • function calling schema 共享同一注册表                │
└──────────────────────┬────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│  ③ Agent 工具执行层                                        │
│     ├─ 旧 24 工具：直接 → modules/persistence              │
│     └─ 新 4 视觉工具：先调 modules/vision.py（豆包）         │
│        ↓                                                   │
│        豆包返回结构化 JSON（amount / category / item ...）   │
│        ↓                                                   │
│        链式调用下游（record_expense / add_course ...）       │
└──────────────────────┬────────────────────────────────────┘
                       ▼
        状态更新 → 主动关怀扫描 → UI/看板同步
```

### 3.2 双模型分工

| 模型 | 职责 | 调用方式 |
|---|---|---|
| **DeepSeek V4-Flash** | 决策 + 工具选择 + 自然语言回复 | OpenAI SDK，function calling |
| **豆包 vision** (`doubao-seed-1-6-vision`) | 图像识别 + 结构化抽取 | OpenAI 兼容接口，content blocks 含 image_url |

两者都通过 OpenAI SDK 调用，只是 base_url 不同。共享同一套连接池单例模式。

### 3.3 视觉风格目标（来自构成主义启发）

| 维度 | 当前 | 目标 |
|---|---|---|
| 主色 | 紫渐变 `#667eea → #764ba2` | 中性 off-white `#F5F2EC` 底 + 黑 `#0A0A0A` + 单一暖红强调 `#D62828` |
| 圆角 | 10px 圆润 | 0-4px 硬边 |
| 阴影 | `box-shadow` 多处毛玻璃 | 几乎不用阴影；用 1px hairline border 和大块色组织层次 |
| 字体 | Streamlit 默认 | Heavy sans-serif headlines（Inter / Geist 700-800） + Regular body |
| 排版 | 对称居中 | 不对称 grid，左对齐为主，标题与正文有大字号跳跃 |
| 装饰 | 渐变 + 阴影 + emoji | 几何块面、强分隔线、克制使用 emoji（仅功能性场景保留） |
| 主动关怀卡片 | 三色渐变背景填充 | 白底 + 5px 严重度色左边框 |

> 注：本期不做"纯粹 1920s 构成主义"。学生用户日常使用需要温暖度，纯黑白会显得冷峻。最终基调是「**构成主义的结构感 + 现代极简的呼吸感 + UniLife 原本的友好底色**」。

### R7-T2 · 豆包视觉客户端封装

- **状态**：`完成`（2026-04-25 13:00 主体；2026-04-25 13:30 endpoint 联调通过 V2/V3 后正式收笔）
- **时间预算**：2h（实际 ~30min）
- **入口条件**：R7-T1 已完成（`DOUBAO_*` 配置就绪）
- **允许改动**：
  - `modules/vision.py`（新建）
  - `requirements.txt`（如需 `Pillow`）
- **禁止改动**：除上面外的所有文件

**动作清单**

1. 新建 `modules/vision.py`，结构：
   ```python
   _client: OpenAI | None = None  # 单例，对应豆包 base_url

   def _get_client() -> OpenAI: ...
   def _vision_call(image_bytes: bytes, prompt: str) -> str: ...

   def recognize_receipt(image_bytes: bytes) -> dict:
       """返回 {amount, item, category, confidence, error}"""

   def recognize_food(image_bytes: bytes) -> dict:
       """返回 {name, calorie_estimate, confidence, error}"""

   def recognize_schedule(image_bytes: bytes) -> dict:
       """返回 {courses: [...], error}"""

   def recognize_packing(image_bytes: bytes, expected_items: list[str]) -> dict:
       """对照 packing_list，返回 {found: [...], missing: [...], error}"""
   ```
2. `_vision_call` 内部：
   - bytes → base64
   - 调豆包 chat.completions.create，content 含 image_url（data URI）
   - 返回模型纯文本（让上层负责解析 JSON）
3. 每个 `recognize_*` 函数：
   - prompt 明确要求"返回 JSON、不要 markdown 代码块"
   - 调 `_vision_call` 拿字符串 → `json.loads` → 加 `error` 字段兜底
4. 错误处理三类：
   - 未配置 KEY → `{"error": "未配置 DOUBAO_API_KEY"}`，不抛
   - 网络 / API 失败 → `{"error": str(e)}`
   - JSON 解析失败 → `{"error": "豆包返回不是有效 JSON: ...原文..."}`

**验收（4 项）**

1. `python -c "from modules.vision import recognize_receipt; print(recognize_receipt(b''))"` 在没图时安全报错（返回 dict 含 error 而非 traceback）。
2. 准备一张样例小票图片（任意）→ 调 `recognize_receipt(image_bytes)` 返回的 dict 包含 amount > 0 / item 非空 / category 在 6 类中。
3. 准备一张课表截图 → 调 `recognize_schedule(image_bytes)` 返回 courses 列表，每条含 name / time / location。
4. mock 网络失败（断网或 base_url 改成不存在）→ 函数返回 `{"error": ...}`，不抛 traceback。

## 7. 决策记录

### 7.1 模型升级走 V4-Flash 而非 V4 标准版

V4-Flash 在 function calling 任务上速度比标准版快 ~2x，且本应用 90% 调用是工具决策（短上下文 + 短回复），用 Flash 不损失质量但提升响应感。如发现 Flash 工具调用准确率明显低于 V3，再切回标准版。

### 7.2 多模态走"豆包视觉 + DeepSeek 文本"双模型而非统一多模态模型

理由：
- DeepSeek 在 function calling 上是当前国内一线水平，换掉决策模型风险大
- 豆包视觉在中文小票 / 课表场景的 OCR 实测好于通用多模态模型
- 双模型分工清晰：vision 负责"看",DeepSeek 负责"决策" — 评审时也好讲故事
- 单点失败风险可控：豆包挂了不影响纯文本路径

### 7.3 视觉风格走"构成主义启发"而非"纯粹 1920s 构成主义"

理由：
- 学生用户每天打开，纯黑白会显得冷峻
- 应用本身有大量数据可视化（看板图表），需要色彩系统支撑
- 保留米色 off-white + 单一暖红，既有构成主义识别度，又不丢友好底色
- 评审视觉评分更看"是否一眼不一样"而非"是否考据严格"

### 7.4 R7 在 R8 之前

理由：
- R7 是功能加法（必须做才能演示多模态卖点），R8 是视觉重塑（演示前任意时段都能做）
- R7 完成后再做 R8，能在新视觉系统下顺手把 vision 工具的 UI（图片预览、缩略图卡片）也照新风格画
- 倒过来做 R8 → R7 的话，R7 加图片上传 UI 时还要再回头适配视觉，重复劳动

### 7.5 不做 streamlit-extras / 自定义 component 救场

R8 全部用 CSS + 现有 streamlit 原生组件实现。不引入 streamlit-extras / 自定义 React component，因为：
- 加依赖意味着加部署复杂度
- Phase 7 的教训：动 streamlit 内部布局容易触发 rerun 循环
- 构成主义视觉要的是"克制 + 几何 + 强对比"，原生组件 + CSS 完全够
